# M0-M4 实验记录

本文件记录真实 PyTorch/Gloo/NCCL 机制 harness 的实验结果。

## M0：PyTorch 行为 harness（Gloo）

状态：**完成（Gloo 部分）**。NCCL/CUDA 部分需在 Linux + NVIDIA GPU 机器上复现。

### 环境

| 项 | 值 |
|---|---|
| 平台 | macOS (Apple Silicon, aarch64, Darwin 25.5.0) |
| Python | 3.12.9（项目 `.venv`，由 `uv` 钉死，与 PATH 无关） |
| PyTorch | 2.13.0（`uv pip install --index-url https://pypi.tuna.tsinghua.edu.cn/simple torch`） |
| Gloo | 可用（CPU） |
| NCCL | 不可用（macOS 无 NCCL/CUDA，`is_nccl_available()=False`） |
| CUDA | 不可用 |
| world size / 拓扑 | 2 rank，单 process group（`gloo`），`tcp://127.0.0.1` rendezvous |

harness：`examples/m0_worker.py`（单 rank worker）+ `examples/run_m0.py`（driver，
对每个场景启动两 rank 子进程并做超时控制）。

### 结果

| 场景 | 行为 | 结论 |
|---|---|---|
| `fifo`（两 rank 均 [A,B]） | COMPLETED，ok=True | 基线：submit→enqueue 约 50µs，wait 约 200–400µs（Gloo CPU） |
| `fixed_reorder`（两 rank 均按计划 [B,A]） | COMPLETED，ok=True | 一致的固定重排是安全的 |
| `identical_reorder_mismatch`（rank0 [A,B]，rank1 [B,A]，相同 all_reduce） | **COMPLETED，ok=True（静默）** | 运行时**无法区分**逻辑上重排的相同 collective；重排检测必须由 plan 层负责 |
| `op_mismatch`（rank0 [all_reduce,all_gather]，rank1 [all_gather,all_reduce]） | **TIMED_OUT（挂起）** | 集合类型不兼容导致 divergence，两 rank 无限阻塞 |
| `missing_collective`（rank0 [A,B]，rank1 [A]） | **TIMED_OUT（挂起）** | rank0 阻塞在第二个 collective，无 peer 到达 |
| `delayed_ready`（rank1 延迟 1s） | COMPLETED，rank0 wait≈1.0s | all_reduce 会等待所有 peer ready（producer-ready 语义在 collective 层已存在） |

### 关键结论（M0 决策关口）

> **当前 API 能否观察和诊断 deferred collective submission？**

可以观察 `submit → enqueue → complete` 的墙钟时序（Gloo 下 `async_op=True` 返回
`Work`，`wait()` 前不阻塞）。但有两个硬边界：

1. **逻辑顺序对 runtime 不可见**：相同 op/size 的 collective 被重排后静默成功，
   运行时没有 identity 可供比对。→ 顺序正确性必须由 plan 层（`TaskKey` 序列 +
   hash 校验）主动暴露，而不是靠 Gloo/NCCL 报错。
2. **divergence 表现为无限挂起**：op 不匹配或缺 collective 时，`Work.wait()`
   无限阻塞（Gloo 无有效 timeout 兜底），必须由上层 watchdog/超时给出有界退出。

这两点直接支撑 architecture.md §6 的正确性模型：**主动暴露 divergence，而非
静默等待 NCCL 超时**。

### 数据（延迟均值，Gloo CPU，1024 float32）

- submit → enqueue（`all_reduce` 返回 `Work`）：~50µs
- enqueue → complete（`wait()` 到所有 peer 完成）：~200–400µs（单 collective）

## M2：V0 同步 admission（Gloo）

状态：**完成**。

### 实现

- `scheduler.py`：`AdmissionScheduler`，训练线程内同步 facade。`submit(intent)`
  先 `validate_intent`（fail-stop），再按 process group 的剩余序列（`_remaining`
  队首）执行 admission：未成队首的 intent 被 parked；producer 未 ready 或
  outstanding 达上限时 delay；满足条件后 `WAITING_FOR_ADMISSION ->
  ADMITTED -> SUBMITTED` 并调用原始 `launch_fn`。
- `work.py`：`ScheduledWork` 支持 create-before-bind——提交即返回，admission
  后由 scheduler `bind` 底层 `Work`；`wait()`/`is_completed()` 透传，完成时
  记录 telemetry 并把 intent 推进到 `COMPLETED`。`get_future()` 留待 M4。
- `telemetry.py`：`now_us()` 单调时钟；`CommTiming` 记录 ready/admit/submit/
  complete 时间戳与实际耗时。

harness：`examples/m2_worker.py`（单 rank worker）+ `examples/run_m2.py`
（driver 启动两 rank 子进程，对比 sequence log）。单元测试
`tests/unit/test_scheduler.py`（13 passed，含 FakeWork 不依赖 Gloo）。

### 结果（两 rank Gloo，1024 float32，env:// rendezvous）

| 场景 | 行为 | 结论 |
|---|---|---|
| `fifo`（按 plan [k0,k1] 提交） | COMPLETED，两 rank launched_seq 相同 | 基线；single collective 约 400–500µs |
| `fixed_reorder`（plan [k1,k0]，按 plan 提交） | COMPLETED，两 rank launched_seq 相同 | 一致的固定重排安全，与 M0 一致 |
| `out_of_order_submit`（plan [k0,k1]，先提交 k1） | COMPLETED，launched_seq 仍为 [k0,k1]，两 rank 相同 | **scheduler 强制计划顺序**：k1 先提交但被 parked，k0 提交后顺带发射 k1 |
| `op_mismatch`（plan 期望 all_reduce，intent 是 all_gather） | 两 rank 均抛 `ValidationError`，有界退出 | **fail-stop**：同类 divergence 在 M0 中是无限挂起，M2 由 plan 校验提前暴露 |

### 关键结论（M2 决策关口）

> **同步 admission 能否在保留正确性的前提下控制 collective 发射？**

可以。通过 per-group 队首约束，scheduler 能在本地延迟/重排发射时机，而不破坏
同一 process group 的诱导序列；乱序提交被显式修正（`out_of_order_submit` 的
ready_ts 顺序与发射顺序相反，但序列仍按 plan）。错误场景从 M0 的「无限挂起 +
外部 kill」变成「fail-stop + 有界退出」，符合 architecture.md §6 的主动暴露模型。

约束记录：

1. M2 是单线程同步 facade（训练线程），scheduler 不加锁；M4 引入 worker
   thread 时再处理并发与锁。
2. `Work.wait()` 只接受 `datetime.timedelta` 超时，`None` 不合法（c10d C++
   签名）；`ScheduledWork.wait` 负责把 `float`/`None` 归一化为 timedelta。
3. parked intent 若队首永不提交，`wait()` 无限阻塞——与 M0 的 missing
   collective 语义等价，仍需 harness 超时兜底。
