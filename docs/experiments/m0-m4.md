# M0-M4 实验记录

本文件记录真实 PyTorch/Gloo/NCCL 机制 harness 的实验结果。

> **M4.5 勘误（2026-09-10）**：M3/M4 当时把 ProcessGroupNCCL
> `Work.wait()` 解释成 CPU 等待 GPU 物理完成，并在 `ScheduledWork.wait()` 中加入
> `torch.cuda.synchronize()`。该观察中“裸 wait 可以在 GPU 完成前返回”是正确的，
> 但这是 CUDA collective 的正常 stream-ordered 语义：wait 会把 NCCL completion
> dependency 插入 caller current stream。M4.5 已删除设备同步，并把 physical
> completion/telemetry/outstanding 改由 completion probe 独立推进。下文保留原始
> M0-M4 记录，涉及“wait 不提前返回”和“设备同步补偿”的结论均以本勘误为准。
> M4.5 的替代 GPU 复验与 WorkNCCL capability 数据见
> [m4.5-gpu3080.md](m4.5-gpu3080.md)。

## M0：PyTorch 行为 harness（Gloo）

状态：**完成（Gloo 部分）**。NCCL/CUDA 部分需在 Linux + NVIDIA GPU 机器上复现。

### 环境

| 项 | 值 |
|---|---|
| 平台 | macOS (Apple Silicon, aarch64, Darwin 25.5.0) |
| Python | 3.12.9（项目 `.venv`，由 `uv` 钉死，与 PATH 无关） |
| PyTorch | 2.13.0（`uv pip install --index-url https://pypi.tuna.tsinghua.edu.cn/simple torch`） |
| Gloo | 可用（CPU） |
| NCCL | 不可用（macOS 无 NCCL/CUDA，`is_nccl_available()=False`） |
| CUDA | 不可用 |
| world size / 拓扑 | 2 rank，单 process group（`gloo`），`tcp://127.0.0.1` rendezvous |

harness：`examples/m0_worker.py`（单 rank worker）+ `examples/run_m0.py`（driver，
对每个场景启动两 rank 子进程并做超时控制）。

### 结果

| 场景 | 行为 | 结论 |
|---|---|---|
| `fifo`（两 rank 均 [A,B]） | COMPLETED，ok=True | 基线：submit→enqueue 约 50µs，wait 约 200–400µs（Gloo CPU） |
| `fixed_reorder`（两 rank 均按计划 [B,A]） | COMPLETED，ok=True | 一致的固定重排是安全的 |
| `identical_reorder_mismatch`（rank0 [A,B]，rank1 [B,A]，相同 all_reduce） | **COMPLETED，ok=True（静默）** | 运行时**无法区分**逻辑上重排的相同 collective；重排检测必须由 plan 层负责 |
| `op_mismatch`（rank0 [all_reduce,all_gather]，rank1 [all_gather,all_reduce]） | **TIMED_OUT（挂起）** | 集合类型不兼容导致 divergence，两 rank 无限阻塞 |
| `missing_collective`（rank0 [A,B]，rank1 [A]） | **TIMED_OUT（挂起）** | rank0 阻塞在第二个 collective，无 peer 到达 |
| `delayed_ready`（rank1 延迟 1s） | COMPLETED，rank0 wait≈1.0s | all_reduce 会等待所有 peer ready（producer-ready 语义在 collective 层已存在） |

### 关键结论（M0 决策关口）

> **当前 API 能否观察和诊断 deferred collective submission？**

可以观察 `submit → enqueue → complete` 的墙钟时序（Gloo 下 `async_op=True` 返回
`Work`，`wait()` 前不阻塞）。但有两个硬边界：

1. **逻辑顺序对 runtime 不可见**：相同 op/size 的 collective 被重排后静默成功，
   运行时没有 identity 可供比对。→ 顺序正确性必须由 plan 层（`TaskKey` 序列 +
   hash 校验）主动暴露，而不是靠 Gloo/NCCL 报错。
2. **divergence 表现为无限挂起**：op 不匹配或缺 collective 时，`Work.wait()`
   无限阻塞（Gloo 无有效 timeout 兜底），必须由上层 watchdog/超时给出有界退出。

这两点直接支撑 `docs/design/architecture.md` §6 的正确性模型：**主动暴露 divergence，而非
静默等待 NCCL 超时**。

### 数据（延迟均值，Gloo CPU，1024 float32）

- submit → enqueue（`all_reduce` 返回 `Work`）：~50µs
- enqueue → complete（`wait()` 到所有 peer 完成）：~200–400µs（单 collective）

## M2：V0 同步 admission（Gloo）

状态：**完成**。

### 实现

- `scheduler.py`：`AdmissionScheduler`，训练线程内同步 facade。`submit(intent)`
  先 `validate_intent`（fail-stop），再按 process group 的剩余序列（`_remaining`
  队首）执行 admission：未成队首的 intent 被 parked；producer 未 ready 或
  outstanding 达上限时 delay；满足条件后 `WAITING_FOR_ADMISSION ->
  ADMITTED -> SUBMITTED` 并调用原始 `launch_fn`。
- `work.py`：`ScheduledWork` 支持 create-before-bind——提交即返回，admission
  后由 scheduler `bind` 底层 `Work`；`wait()`/`is_completed()` 透传，完成时
  记录 telemetry 并把 intent 推进到 `COMPLETED`。`get_future()` 留待 M4。
- `telemetry.py`：`now_us()` 单调时钟；`CommTiming` 记录 ready/admit/submit/
  complete 时间戳与实际耗时。

harness：`examples/m2_worker.py`（单 rank worker）+ `examples/run_m2.py`
（driver 启动两 rank 子进程，对比 sequence log）。单元测试
`tests/unit/test_scheduler.py`（13 passed，含 FakeWork 不依赖 Gloo）。

### 结果（两 rank Gloo，1024 float32，env:// rendezvous）

| 场景 | 行为 | 结论 |
|---|---|---|
| `fifo`（按 plan [k0,k1] 提交） | COMPLETED，两 rank launched_seq 相同 | 基线；single collective 约 400–500µs |
| `fixed_reorder`（plan [k1,k0]，按 plan 提交） | COMPLETED，两 rank launched_seq 相同 | 一致的固定重排安全，与 M0 一致 |
| `out_of_order_submit`（plan [k0,k1]，先提交 k1） | COMPLETED，launched_seq 仍为 [k0,k1]，两 rank 相同 | **scheduler 强制计划顺序**：k1 先提交但被 parked，k0 提交后顺带发射 k1 |
| `op_mismatch`（plan 期望 all_reduce，intent 是 all_gather） | 两 rank 均抛 `ValidationError`，有界退出 | **fail-stop**：同类 divergence 在 M0 中是无限挂起，M2 由 plan 校验提前暴露 |

### 关键结论（M2 决策关口）

> **同步 admission 能否在保留正确性的前提下控制 collective 发射？**

可以。通过 per-group 队首约束，scheduler 能在本地延迟/重排发射时机，而不破坏
同一 process group 的诱导序列；乱序提交被显式修正（`out_of_order_submit` 的
ready_ts 顺序与发射顺序相反，但序列仍按 plan）。错误场景从 M0 的「无限挂起 +
外部 kill」变成「fail-stop + 有界退出」，符合 `docs/design/architecture.md` §6 的主动暴露模型。

约束记录：

1. M2 是单线程同步 facade（训练线程），scheduler 不加锁；M4 引入 worker
   thread 时再处理并发与锁。
2. `Work.wait()` 只接受 `datetime.timedelta` 超时，`None` 不合法（c10d C++
   签名）；`ScheduledWork.wait` 负责把 `float`/`None` 归一化为 timedelta。
3. parked intent 若队首永不提交，`wait()` 无限阻塞——与 M0 的 missing
   collective 语义等价，仍需 harness 超时兜底。

## M3：CUDA event ready 语义（NCCL）

状态：**完成**。实现 + 单测（35 unit + 3 GPU）+ 两 rank NCCL harness 全绿。

### 环境（远端 2× RTX 3090）

| 项 | 值 |
|---|---|
| 平台 | AutoDL/seetacloud 盒子，2× RTX 3090（24GB），NVIDIA driver 595.71.05 |
| Python / PyTorch | miniconda3 / torch 2.12.1+cu130（CUDA 13.2） |
| NCCL | 可用；两 rank，每进程 `CUDA_VISIBLE_DEVICES=<rank>` 绑定单卡 |
| rendezvous | `env://`（`MASTER_ADDR=127.0.0.1` + 随机端口） |

代码同步：`rsync` 到 `gpu3090:/root/autodl-tmp/runtime-comm-scheduler`（`~/.ssh/config`
别名 `gpu3090`，端口 12548）。

### 实现（相对 M2 的改动）

- `scheduler._sync_ready_event(intent)`：发射前让 `current_stream().wait_event(ev)`，
  把 collective 排在 producer 的 GPU 工作之后（stream-ordered，GPU 侧依赖边），
  而非 CPU 阻塞。`threading.Event` 的 CPU ready 仍在 `_is_ready` 处理。
- `work._ensure_gpu_complete(underlying)`：对 c10d Work 在底层 `wait()` 后补一次
  `torch.cuda.synchronize()`，保证 `ScheduledWork.wait()` 的完成信号真实反映 GPU
  完成（见下方关键发现 #2）。M4 计划换成 comm-stream completion event 消除全同步。
- `examples/m3_worker.py` + `examples/run_m3.py`：两 rank NCCL harness，跑在
  `torch.profiler` 下并导出 chrome trace 到 `/root/autodl-tmp/m3_traces/`。
- `tests/gpu/test_cuda_semantics.py`：3 个单卡测试，无 CUDA 时整体 skip。

### 结果（两 rank NCCL，验收通过）

| 场景 | 行为 | 结论 |
|---|---|---|
| `fifo`（[k0,k1]） | COMPLETED，两 rank launched_seq 相同，ok=True | 基线；预热后单 collective 约 200–900µs |
| `fixed_reorder`（[k1,k0]） | COMPLETED，序列一致，ok=True | 固定重排安全，与 M0/M2 一致 |
| `delayed_ready`（side stream 慢 producer + ready_ev） | ok=True，数据正确 | **stream dependency 正确**：collective 排在 producer 之后 |
| `no_wait_ready`（同 producer，**不**带 ready_ev） | ok=False（两 rank） | **竞争演示成立**：无依赖边时 collective 与 producer 竞争，读到未就绪数据 |
| `op_mismatch`（plan 期望 all_reduce，intent 是 all_gather） | 两 rank 均抛 `ValidationError` | fail-stop，与 M2 一致 |
| `wait_no_early_return`（慢 GPU 工作 + 较大 collective） | comp event wait 前 False、wait 后 True；wait() 阻塞 41–403ms | **wait() 不提前返回**（由 `_ensure_gpu_complete` 保证） |

### 关键发现（M3 决策关口）

> **naive CUDA event 能否表达 NCCL collective 的 ready/completion？**

不能直接表达，需要两层补偿：

1. **NCCL 跑在独立 comm stream，naive 记在当前 stream 的 event 不追踪 NCCL
   完成**。当前 stream 空闲时，`event.record(current_stream)` 立即触发，与
   collective 的 GPU 完成无关。要表达"collective 完成"，完成信号必须来自 comm
   stream（c10d 内部），scheduler 侧拿到的是 `Work` 而非 comm-stream event。
2. **裸 `WorkNCCL.wait()` 在本环境（torch 2.12.1+cu130）不保证 GPU 完成**。
   实测：4GB all_reduce，`wait()` 返回 ~0.01ms，而 GPU 工作要等后续
   `torch.cuda.synchronize()` 才排空（~570ms）。即 wait 返回不意味着 collective
   完成——harness 早前 `actual_us=55ms` 但 `wait_s=0.0` 的矛盾即由此而来
   （profiler 干扰 + `.item()` 隐式同步掩盖了真实现象）。→
   `ScheduledWork.wait()` 对 c10d Work 补一次设备同步，把"完成"变成硬保证。
3. **默认（legacy）stream 会与所有其他 stream 隐式同步**。world_size=1 的
   `all_reduce(async_op=True)` 在默认流上实测阻塞 ~300ms 等一个无关 side-stream
   producer，掩盖依赖边；NCCL 首 op 还有 ~350ms lazy init。单卡测试须用非
   legacy 显式流 + 预热 communicator 才能观察依赖边（真实训练中 collective 走
   comm stream，无隐式同步，故两 rank harness 不受影响）。

这些发现直接影响 M4：异步 worker 不能依赖 `Work.wait()` 或当前 stream event 做
完成通知，需要 comm-stream completion event（或接受一次性的设备同步）。

## M4：异步 admission worker（NCCL）

状态：**完成**。实现 + 单测（44 unit，其中 9 个 worker 模式）+ 两 rank NCCL
harness 全绿。

### 环境

同 M3（2× RTX 3090，torch 2.12.1+cu130，NCCL，env:// rendezvous）。

### 决策关口：worker 线程提交 ProcessGroupNCCL 是否足以支撑 prototype？

结论：**单 worker 线程提交可靠（gate 通过）；同一 communicator 多线程并发
提交不安全（gate 记录了这条硬限制）。** 对应实验 `examples/m4_gate_worker.py`
+ `examples/run_m4_gate.py`（两 rank，各绑一张 3090）：

| 场景 | 结果 |
|---|---|
| `worker_basic`（非主线程串行提交/等待 32 个 all_reduce） | ok=True，数据全对，总耗时 ~4ms |
| `producer_continues`（主线程入队即返回，worker 异步 drain） | enqueue ~0.1ms << worker ~37ms，GPU 计算与 collective 重叠 |
| `concurrent_submit`（主线程 + worker **同时**向同一 communicator 并发提交） | **打挂整个盒子**（进程自旋占满 CPU，SSH 不可达，需几分钟恢复） |

第三条是信息性场景（M4 设计中只有 worker 一个提交线程，不涉及并发），但它
**实证了 c10d/NCCL 对同一 communicator 的双线程并发提交没有安全保证**——比
记录限制更硬的是直接打挂进程。另观察到：producer 若在纯 Python 忙循环中攥住
GIL 会完全饿死 worker 线程（该场景第二次打挂盒子是我测量脚本的 bug）；真实
训练循环中 producer 调 CUDA（释放 GIL），worker 能及时被调度。

### 实现（相对 M3 的改动）

- `scheduler.py`：`AdmissionScheduler` 增加 `worker=True` 模式。
  - 训练线程的 `submit` 只做校验 + park + 唤醒，**立即返回**（不阻塞）；
  - 专门的 worker 线程被唤醒后逐个 group `_drain` 发射（deferred launch 移到
    worker）；共享状态用一把锁保护；`close()` 停止并 join worker；
  - 发射时在 scheduler 持有的**显式 communication stream**（非 legacy）上下文中
    调用 `launch_fn`：`ready_event` 的 `wait_event` 落在该 stream 上，collective
    经 c10d 捕获该 stream 状态 -> producer stream -> comm stream 的依赖边
    （现见 `docs/design/scheduler-stream-dependency.md`）；
  - worker 内 `launch_fn` 抛错时记录到 `_worker_error`，下一次
    submit/nudge/观察接口在训练线程上重新抛出（fail-stop）；
  - 同步模式（`worker=False`，M2/M3 行为）原样保留，35 个既有单测无回归。
- `work.py`：`get_future()` 落地（M2 遗留）。返回 `ScheduledFuture`，
  `result()` 内部走 `wait()`（含 M3 的设备同步补偿），`done()` 透传
  `is_completed()`——完成检测需要设备同步，因此 future 不是零开销异步回调。

### 结果（两 rank NCCL，验收通过）

| 场景 | 行为 | 结论 |
|---|---|---|
| `fifo`（worker 模式，[k0,k1]） | COMPLETED，两 rank launched_seq 相同，ok=True | 基线；单 collective ~300–1100µs |
| `fixed_reorder`（[k1,k0]） | COMPLETED，序列一致，ok=True | 固定重排安全，与 M0/M2/M3 一致 |
| `out_of_order_submit`（先提交 k1） | COMPLETED，launched_seq 仍为 [k0,k1]，两 rank 相同 | **worker 仍强制计划顺序**：k1 被 parked，k0 提交后 worker 顺带发射 k1 |
| `delayed_ready`（慢 producer + ready_ev，经 worker/comm stream） | ok=True，实际 ~15.5ms | **stream dependency 正确**：worker 在 comm stream 上 wait_event，collective 排在 producer 之后 |
| `no_wait_ready`（无 ready_ev） | ok=False（两 rank） | 竞争演示成立：无依赖边时读到未就绪数据 |
| `producer_overlap`（16 个 intent + producer 继续 GPU 计算） | 全部 ok=True；enqueue ~0.3ms，compute 开始时机 worker 仍在 drain | **producer 提交后继续执行**：submit 不阻塞，计算与 collective 重叠 |
| `op_mismatch`（plan 期望 all_reduce，intent 是 all_gather） | 两 rank 均抛 `ValidationError` | fail-stop，有界退出 |

### 关键发现（M4 决策关口）

> **Python 单 worker 线程提交 ProcessGroupNCCL 是否足以支撑 prototype？**

可以。验收三要素全部成立：producer 提交后继续执行（`producer_overlap` 入队
~0.3ms、计算与 collective 重叠）；consumer 经 `ScheduledWork.wait()` 等待且不
提前返回（沿用 M3 的设备同步补偿）；没有错误的 stream dependency 或 sequence
divergence（7 场景两 rank sequence log 全一致，`delayed_ready` 依赖正确、
`out_of_order_submit` 顺序强制正确）。

硬限制与已知代价：

1. **同一 communicator 绝不允许多线程并发提交**（关口实测打挂进程）。M4
   设计只有 worker 一个提交线程，天然避开；若未来需要多提交线程，必须引入
   显式提交串行化（当前未验证的锁机制不可掩盖问题）。
2. **M3 遗留的全设备同步未消除**。M3 曾计划 M4 换 comm-stream completion
   event 消除 `_ensure_gpu_complete` 的 `torch.cuda.synchronize()`；实测 c10d
   Work 不暴露 NCCL comm stream 的完成 event（naive 记在当前 stream 的 event
   不追踪 comm stream 完成，M3 发现 #1），public API 无法在「communication
   completion -> completion event -> consumer stream」（§4.5 后半段）上拿到
   完成信号。要消除全同步需自定义 ProcessGroup/C++ enforcer（architecture
   §8 演进路线的下一层），或 c10d 暴露 WorkNCCL 内部 event——超出 M4 范围，
   记录为后续工作。
3. **worker 发射时持有调度锁**：`launch_fn` 是 async_op 的 enqueue（约百微
   秒），锁内发射可接受；但若 launch_fn 阻塞（如 NCCL rendezvous），训练线程
   的 submit 会等锁。
4. **producer 持 GIL 的纯 CPU 忙循环会饿死 worker**；训练循环调 CUDA（释放
   GIL），不影响真实场景。
5. `get_future()` 是 `wait()` 的便利接口而非零开销异步回调（完成检测需要
   设备同步）。
