## 1. 背景

Phase 1 的 M0-M4 已建立以下能力：

- 确定性的 `TaskKey`、`CommIntent` 和共享 `Plan`；
- plan/metadata/per-process-group sequence 校验；
- deferred collective admission；
- 独立 worker thread；
- CUDA producer ready event 到 ProcessGroupNCCL 的依赖桥接；
- `ScheduledWork` 延迟绑定；
- Gloo、NCCL 和 CUDA harness。

重构前的本地基线为：

```text
44 passed, 3 skipped
```

M4 之后暴露出两个需要在继续 M5/M6 前修正的架构问题。

### 1.1 Scheduler 同时保留同步和 worker 两套路径

`AdmissionScheduler` 为兼容 M2/M3，仍允许：

```text
worker=False: training thread 直接 admission + launch
worker=True:  独立 worker admission + launch
```

这造成了以下问题：

- 公共方法和内部状态访问存在大量 `_worker_mode` 分支；
- `_drain()`、completion callback 和锁语义需要同时适配两种执行模型；
- 无法把“每个 rank/GPU 只有一个 host launch sequencer”表达成结构性不变量；
- 后续跨 communicator 调度容易意外重新引入多线程 launch；
- M2/M3 的历史实验模型开始限制当前架构，而不是只作为历史证据存在。

### 1.2 `ScheduledWork.wait()` 被错误解释为 GPU 物理完成等待

当前实现会在底层 `Work.wait()` 后调用：

```python
torch.cuda.synchronize()
```

其目的是确保 `wait()` 返回时 GPU collective 已经物理完成。但这不是普通
ProcessGroupNCCL `Work.wait()` 的设计语义。

对 NCCL work，正常的 `wait()` 语义是：

```text
NCCL completion event -> 调用 wait() 时的 current CUDA stream
```

也就是向 consumer stream 插入 GPU-side dependency。CPU 可以在 NCCL kernel
真正执行完成前返回；consumer stream 上排在 `wait()` 之后的操作仍然不会提前使用
collective 输出。

PyTorch 文档和 ProcessGroupNCCL 当前实现可参考：

- [PyTorch distributed：Asynchronous operation](https://docs.pytorch.org/docs/stable/distributed.html#synchronous-and-asynchronous-collective-operations)
- [ProcessGroupNCCL.hpp：WorkNCCL wait/isCompleted 契约](https://github.com/pytorch/pytorch/blob/main/torch/csrc/distributed/c10d/ProcessGroupNCCL.hpp)
- [ProcessGroupNCCL.cpp：synchronizeStream/wait 实现](https://github.com/pytorch/pytorch/blob/main/torch/csrc/distributed/c10d/ProcessGroupNCCL.cpp)

因此，现有全设备同步：

- 破坏了原 collective 的异步 CPU/GPU 语义；
- 同步了与当前 communication 完全无关的 stream；
- 降低计算通信重叠；
- 把 consumer dependency installation 和 physical completion 混成一个事件；
- 使 outstanding slot 释放和 telemetry completion 依赖 consumer 是否调用
  `ScheduledWork.wait()`。

## 2. 重构目标

M4.5 建立以下不可变边界：

1. 每个 rank/GPU 只有一个 scheduler-owned launch worker。
2. 所有受 scheduler 管理的 communicator 都从这个 worker 提交到底层
   ProcessGroup。
3. training thread 的 `submit()` 只校验、park 和唤醒 worker，不调用
   `launch_fn`。
4. scheduler 使用共享 plan 的本地投影形成统一的 rank-wide host launch order。
5. producer dependency 通过 ready event 和 bridge stream 传入 ProcessGroup。
6. consumer dependency 通过底层 `Work.wait()` 传回调用时的 current stream。
7. 普通依赖传递路径不调用 device synchronize、stream synchronize 或 event 的
   CPU synchronize。
8. physical completion 由独立 completion tracker 观察，不由 consumer `wait()`
   推进。
9. launch、scheduler、底层 Work 或 shutdown 错误必须唤醒相关
   `ScheduledWork`，不能留下永久等待的未绑定对象。
10. 已提交到底层 ProcessGroup 的 collective 不取消、不回退、不重新排序。

## 3. 非目标

本次重构不实现：

- Megatron DP adapter；
- iteration 间 plan 分发和版本切换；
- 动态 criticality/slack/bandwidth policy；
- 偏序 DAG 或 ready-frontier 调度；
- 多 worker 并发 launch；
- 自定义 C++ ProcessGroup；
- NCCL channel、algorithm 或 chunk 控制；
- CUDA Graph 内部 collective 的拆分调度；
- 跨 rank 的实时 coordinator。

M4.5 首先采用保守全序。只有在全序的 head-of-line blocking 被真实训练实验确认后，
才进入偏序 DAG 设计。

## 4. 目标架构

```text
training/framework thread
  |
  | capture device + ready_event + strong references
  | scheduler.submit(intent)
  v
rank-local pending table
  |
  | shared-plan local projection + admission
  v
single launch worker / host launch sequencer
  |
  | device guard
  | bridge stream waits producer ready_event
  | async ProcessGroup call
  v
underlying c10d Work
  |                                  |
  | ScheduledWork.wait()             | completion probe
  | called on consumer stream        | observes physical completion
  v                                  v
consumer stream dependency      COMPLETED telemetry
                                outstanding slot release
```

职责边界：

```text
AdmissionScheduler
  - plan projection
  - pending/admission/inflight state
  - rank-wide launch order
  - worker lifecycle and fail-stop

LaunchExecutor
  - local CUDA device/stream context
  - ready dependency bridge
  - invoke rank-local launch_fn

ScheduledWork
  - wait for deferred bind
  - delegate consumer wait semantics
  - expose completion query
  - propagate bind/launch failure

CompletionProbe
  - backend-specific physical-completion observation
```

## 5. `Work.wait()` 与完成语义

### 5.1 必须区分的事件

| 事件 | 定义 | 是否表示 GPU 物理完成 |
|---|---|---:|
| intent captured | framework 已创建本地通信请求 | 否 |
| ready dependency captured | producer stream 已记录 ready event | 否 |
| admitted | scheduler 已允许任务进入 launch | 否 |
| submitted/bound | ProcessGroup 调用已返回 underlying Work | 否 |
| wait inserted | `Work.wait()` 已把 completion dependency 插入 consumer stream | 否 |
| completed | backend completion probe 观察到 operation 物理完成 | 是 |

### 5.2 新的 `ScheduledWork.wait()` 契约

```text
1. 等待 ScheduledWork 进入 BOUND 或 FAILED；
2. FAILED 时重新抛出原始错误；
3. BOUND 后调用真实 Work.wait()；
4. 返回底层 Work.wait() 的结果；
5. 不调用任何额外 CUDA synchronize；
6. 不在返回时把 intent 标记为 COMPLETED。
```

对于 CUDA/NCCL，调用者必须在实际 consumer device/stream context 中调用
`ScheduledWork.wait()`。否则底层 completion dependency 会被插入错误的 stream。

对于 CPU/Gloo，底层 `wait()` 可以阻塞 CPU 到 operation 完成。wrapper 不试图把
不同 backend 强行统一为同一种 host-blocking 行为，而是保留底层 Work 契约。

如果传入有限 timeout，应使用一个总 deadline：等待 bind 消耗的时间必须从传给
underlying Work 的 timeout 中扣除。需要同时记录：对 ProcessGroupNCCL，显式有限
timeout 或 `TORCH_NCCL_BLOCKING_WAIT=1` 可能使底层 `wait()` 阻塞 CPU 到物理完成；
wrapper 不应覆盖这一 backend 配置。

### 5.3 物理完成

`COMPLETED`、`complete_ts` 和 outstanding slot 释放由 completion tracker 驱动。

第一版 `WorkIsCompletedProbe` 调用：

```python
underlying.is_completed()
```

当前 ProcessGroupNCCL 实现使用 NCCL end event 查询 GPU execution completion。
但 PyTorch 的通用文档与不同 backend/version 的实现可能存在差异，因此这必须是
一个经过目标环境 gate test 验证的 backend capability，而不能成为未验证的全局
假设。

规则：

- 已验证 backend：允许 physical completion telemetry 和 `max_outstanding`；
- 不具备可靠 completion probe 的 backend：若配置 `max_outstanding > 0`，初始化
  直接失败；
- 禁止退化为 `torch.cuda.synchronize()`；
- 禁止把 consumer `wait()` 当作 physical completion probe。

### 5.4 `get_future()`

本次建议删除当前自定义 `ScheduledFuture`：

- 它不是完整的 `torch.futures.Future`；
- `result()` 只是再次调用 `ScheduledWork.wait()`；
- 它没有兑现 CUDAFuture callback stream 的语义；
- M5 的 Megatron `start_grad_sync/finish_grad_sync` 只需要 Work-like `wait()`。

如果后续 DDP communication hook 或其他真实调用点要求 future，应基于实际的
`underlying.get_future()` 单独设计 deferred CUDAFuture bridge，而不是保留当前的
便利包装。

审批项见本文第 15 节。

## 6. Plan 本地投影与跨 Communicator 顺序

### 6.1 当前问题

当前 scheduler 为每个 process group 建立独立 `_remaining`，worker 再按 group
遍历和 drain。这只能保持各 group 内部顺序，不能保持 rank-wide 全局投影。

例如：

```text
global plan: A0 -> B0 -> A1
```

如果 A0、B0、A1 都已经 pending，按 group drain 可能发射为：

```text
A0 -> A1 -> B0
```

这不符合保守全序，也可能在重叠 communicator 拓扑中与其他 rank 的局部决定形成
循环顺序。

### 6.2 本地投影

Plan 继续是全 rank 共享的规范文档。Scheduler 根据本 rank 参与的 logical group
集合生成本地 key 序列：

```python
def local_projection(
    self,
    local_group_ids: Collection[str],
) -> tuple[TaskKey, ...]:
    return tuple(
        key for key in self.keys
        if key.process_group_id in local_group_ids
    )
```

不参与某 group 的 rank 跳过对应 task，不创建占位 collective。

第一版构造器要求 adapter 显式传入 `local_group_ids`。在 M6 plan 分发前，再决定
是否增加：

```python
@dataclass(frozen=True)
class GroupSpec:
    group_id: str
    member_ranks: tuple[int, ...]
```

若增加 `GroupSpec`，它必须进入 plan digest。M4.5 不强制立即改变 plan wire schema，
避免把 plan distribution 工作提前混入本次重构。

### 6.3 新的 scheduler 数据结构

```python
_remaining: deque[TaskKey]                 # rank-wide local projection
_pending: dict[TaskKey, PendingTask]
_launching: PendingTask | None             # 已 reserve、正在调用 launcher
_inflight: dict[TaskKey, ScheduledWork]
_submitted: set[TaskKey]                   # duplicate validation
_launch_log: list[TaskKey]                 # rank-wide host launch order
_timings: dict[TaskKey, CommTiming]
```

如需继续输出 per-group sequence log，应从 `_launch_log` 过滤得到，不再维护多份可
独立变化的 launch truth。

### 6.4 全局 outstanding

`max_outstanding` 改为每个 rank/GPU 的全局上限：

```text
outstanding = len(_inflight) + (1 if _launching else 0)
```

不能让每个 process group 分别获得一份上限，否则多个 group 会把实际 in-flight
总量放大。

全序只限制 host submission order，不要求等待前一个 collective 完成后再提交
下一个。因此 `max_outstanding=0` 时，worker 仍会快速连续 launch，多 communicator
GPU overlap 仍由 ProcessGroup/NCCL 决定。

## 7. Scheduler 线程模型

### 7.1 公共接口草案

```python
class AdmissionScheduler:
    def __init__(
        self,
        plan: Plan,
        *,
        local_group_ids: Collection[str],
        executor: LaunchExecutor,
        completion_probe: CompletionProbe | None = None,
        max_outstanding: int = 0,
        completion_poll_interval_s: float = 0.001,
    ): ...

    def submit(self, intent: CommIntent) -> ScheduledWork: ...
    def nudge(self) -> None: ...
    def sequence_log(self) -> list[TaskKey]: ...
    def group_sequence_log(self) -> dict[str, list[TaskKey]]: ...
    def timings(self) -> list[CommTiming]: ...
    def finish_window(self, timeout: float | None = None) -> None: ...
    def close(self) -> None: ...
```

删除：

```text
worker=False/True
comm_stream constructor argument
nudge(group_id=...)
training-thread _drain path
```

bridge stream 由 execution plane 创建和持有，不由调用方当成普通 scheduler 参数
注入。测试若需要自定义 stream，可通过 executor 构造参数注入。

### 7.2 `submit()`

`submit()` 必须只做有界 CPU 工作：

```text
validate plan metadata
validate key belongs to local projection
validate not duplicate / scheduler is RUNNING
CREATED -> READY -> WAITING_FOR_ADMISSION
create CommTiming and ScheduledWork
insert PendingTask
condition.notify()
return ScheduledWork
```

`submit()` 不查询 CUDA event 是否触发。ready event 表示一个 GPU dependency token，
不是要求 host 等待的 admission gate。

测试使用的 `threading.Event` 属于 CPU-side admission gate，可以在 scheduler 选择
任务时查询；event 被设置后由 `nudge()` 唤醒 worker。

### 7.3 Worker loop

建议用一个 `threading.Condition` 管理共享状态，替代 `_lock + _wake + _stop`。

概念伪代码：

```python
while True:
    completed = snapshot_inflight_for_poll()
    poll_completion_outside_lock(completed)
    commit_completed_under_lock()

    with condition:
        if scheduler_should_stop():
            break

        task = reserve_next_launchable_task()
        if task is None:
            condition.wait(timeout=poll_interval_if_inflight_else_none)
            continue

    # Only this worker can reach this point. Do not hold scheduler state lock.
    try:
        underlying = executor.launch(task.intent)
        validate_underlying_work(underlying)
    except BaseException as exc:
        fail_scheduler_and_unbound_work(exc)
        break

    with condition:
        task.work.bind(underlying)
        task.intent.transition(SUBMITTED)
        register_inflight_and_launch_log(task)
        condition.notify_all()
```

状态 reserve 和真实 launcher 调用之间用 `_launching` 显式表示。只有 worker 能
reserve/launch，所以释放 scheduler lock 不会允许其他线程越过当前 launch order。

### 7.4 不在状态锁中 launch

`launch_fn` 是外部边界：即使预期是快速的 async enqueue，也可能因为 lazy init、
rendezvous、Python callback 或错误处理而变慢。

因此：

- 在锁内选任务和 reserve；
- 在锁外调用 executor/`launch_fn`；
- 在锁内 commit underlying Work；
- training thread 在 launcher 较慢时仍可继续 submit 后续 intent。

## 8. Execution Plane

新增建议文件：

```text
src/runtime_comm_scheduler/executor.py
```

### 8.1 接口

```python
class LaunchExecutor(Protocol):
    def launch(self, intent: CommIntent) -> Any:
        """Return an asynchronous backend Work."""
```

### 8.2 PyTorch/CUDA 实现

```python
class TorchProcessGroupExecutor:
    def __init__(self, device):
        self.device = device
        self.gate_streams = {}

    def launch(self, intent):
        group_id = intent.key.process_group_id
        with torch.cuda.device(self.device):
            gate = self.gate_streams.get(group_id)
            if gate is None:
                gate = self.gate_streams[group_id] = torch.cuda.Stream()
            with torch.cuda.stream(gate):
                if intent.ready_event is not None:
                    gate.wait_event(intent.ready_event)
                return intent.launch_fn()
```

这里的“单 launch worker”不等于“单 CUDA gate stream”。如果不同 communicator
共用一条 gate stream，stream 内的顺序会使后一个 intent 不必要地继承前一个
intent 的 producer-ready 依赖，形成跨 communicator head-of-line blocking。
因此第一版应按 `(device, process_group_id)` 持有 gate stream：同一 group 内的
collective 本来就必须有序，不同 group 的 GPU ready dependency 则保持独立。
rank-wide host launch order 仍由唯一 worker 保证。

必须校验：

- intent tensor/device 与 executor device 一致；
- ready event 属于兼容 device；
- `launch_fn` 存在；
- `launch_fn` 返回一个符合 Work-like protocol 的异步对象；
- scheduler 管理的 launcher 不允许使用 `async_op=False`；
- 所有 communicator 使用同一个 executor worker，但 NCCL stream 仍由各
  ProcessGroup 管理。

这里应使用 `bridge_stream` 或 `gate_stream` 命名。它不是 NCCL communication
stream；其职责只是把 producer dependency 传给 ProcessGroup caller-stream
语义。

### 8.3 CPU/Gloo 与测试实现

提供不接触 CUDA 的 executor：

```python
class DirectLaunchExecutor:
    def launch(self, intent):
        return intent.launch_fn()
```

它仍然只能由 scheduler worker 调用。“Direct”表示无 CUDA bridge，不表示在
training thread 同步调用。

## 9. `CommIntent` 与对象生命周期

建议增加：

```python
device: Any = None
keepalive: tuple[Any, ...] = ()
```

其中：

- `tensor` 继续保留主要通信 tensor 的强引用；
- `keepalive` 显式保存独立 input/output、flatten buffer、temporary storage 或
  launcher 依赖的其他对象；
- `process_group` 保存 rank-local ProcessGroup handle；
- `ready_event` 必须在 intent 创建点实际 producer current stream 上记录；
- scheduler pending record 和 `ScheduledWork` 在 bind 前都持有 intent；
- bind 后 underlying c10d Work 负责其内部 allocator safety，应用仍负责输出
  tensor 的正常生命周期。

不要依赖 `launch_fn` closure 恰好捕获所有必要对象作为唯一生命周期保证。

## 10. 状态机

### 10.1 Intent state

```text
CREATED
   |
   v
READY                    ready dependency 已捕获
   |
   v
WAITING_FOR_ADMISSION    已进入 pending
   |
   v
ADMITTED                 worker 已 reserve
   |
   v
SUBMITTED                已越过 ProcessGroup 调用边界
   |
   +---------------------> COMPLETED
   |
   +---------------------> FAILED

CREATED/READY/WAITING/ADMITTED --error--> FAILED
```

`SUBMITTED` 仍是不可取消边界。`FAILED` 表示该 task 不再能正常完成；对于 launcher
在部分提交后抛错的极端情况，系统进入 fail-stop，不尝试恢复 communicator。

### 10.2 Scheduler state

```text
RUNNING -> CLOSING -> CLOSED
   |
   v
FAILED -> CLOSED
```

所有公共方法进入时检查 scheduler state。`close()` 必须幂等，并保证 worker 已
join；即使 scheduler 已经 FAILED，也不能在 join 前直接重新抛出错误。

### 10.3 ScheduledWork binding state

```text
UNBOUND -> BOUND
   |
   v
FAILED
```

使用 `Condition` 同时等待 bind 和错误，避免 worker 异常、missing head 或 close
留下永久阻塞的 `_launched.wait()`。

## 11. 异常、关闭与 Window 结束

### 11.1 Launch 失败

worker 调用 executor/launcher 失败时：

1. 当前 `_launching` work 调用 `fail(exc)`；
2. scheduler 状态变为 `FAILED`；
3. 所有尚未绑定的 pending work 调用 `fail(SchedulerFailedError(...))`；
4. 唤醒所有 condition waiter；
5. worker 停止 launch 新任务；
6. 已经提交的 work 不取消；
7. 下一次 scheduler 公共方法调用重新暴露根因。

### 11.2 底层异步 Work 失败

completion probe 或 consumer `wait()` 抛出底层异常时：

- 对应 intent 转为 `FAILED`；
- telemetry 记录 `error_ts`、`error_stage="completion"`；
- scheduler 进入 fail-stop；
- 不继续提交后续 collective，避免 communicator sequence 在 rank 间进一步分叉。

### 11.3 `close()`

建议语义：

- 拒绝新 submit；
- fail 所有未绑定 work；
- 停止 launch 新任务；
- 唤醒并 join worker；
- 不取消已提交 collective；
- join 后再重新报告保存的 worker error；
- 重复调用安全。

### 11.4 `finish_window()`

与资源关闭分开提供：

```text
finish_window(timeout)
  - 验证 local projection 中没有 missing key
  - 验证 pending/launching 已清空
  - 等待或检查 inflight physical completion
  - 输出有界 timeout 和缺失 key 诊断
```

M6 plan 切换应调用 `finish_window()`，而不是把 iteration drain 语义塞进
`close()`。

## 12. Telemetry 调整

当前 `ready_ts/admit_ts/submit_ts/complete_ts` 容易把 host observation 和 GPU
event 混淆。建议使用：

```python
intent_ts: int | None
ready_record_ts: int | None
admit_ts: int | None
launch_start_ts: int | None
submit_ts: int | None
first_wait_ts: int | None
complete_ts: int | None
error_ts: int | None
error_stage: str | None
predicted_duration_us: float | None
actual_duration_us: float | None
```

定义：

- `ready_record_ts` 是 host 记录 ready event 的时间，不宣称 GPU producer 已完成；
- `submit_ts` 是底层异步 ProcessGroup 调用返回的 host 时间；
- `first_wait_ts` 只表示 consumer 首次请求接入依赖；
- `complete_ts` 是 completion probe 第一次观察到物理完成的 host 时间；
- `actual_duration_us = complete_ts - submit_ts`，精度受 poll interval 影响；
- 需要精确 GPU duration 时使用 CUDA event/profiler，不用 host timestamp 冒充。

## 16. 审批项

以下决策已于 2026-09-10 全部按建议批准并落实：

### A. 是否完全删除同步 scheduler 模式

决策：**删除**。

理由：同步 API 语义可由 adapter 在 training thread 调用 `ScheduledWork.wait()`
实现，不需要第二套 admission/launch 路径。

### B. 是否删除当前自定义 `ScheduledFuture`

决策：**删除**，等真实 framework integration 提出 future 需求后重新设计。

### C. `local_group_ids` 是否作为必填构造参数

决策：**必填**。

理由：scheduler 必须在开始执行前区分 non-local task 与尚未到达的 local task。

### D. `GroupSpec(member_ranks)` 是否在 M4.5 进入 Plan

决策：**暂缓到 M6**，M4.5 只实现显式 `local_group_ids` 和投影。

理由：本次先解决线程/stream/顺序核心问题，避免提前扩展 plan 分发 schema。

### E. Completion tracker 使用 polling 还是 Future callback

决策：**第一版使用可配置 polling + backend capability gate**。

理由：`is_completed()` 路径简单且可验证；PyTorch CUDAFuture 有独立 callback
stream 语义，不应在本次顺手实现一个不完整代理。

### F. 是否增加 `IntentState.FAILED`

决策：**增加**。

理由：当前生命周期无法表达 launch/completion/shutdown 失败，容易留下看似仍可
推进的 intent。

### G. `close()` 与 `finish_window()` 是否分离

决策：**分离**。

理由：资源关闭和 iteration/plan drain 是不同协议；M6 需要后者，但不应销毁整个
scheduler。

## 17. 完成定义

只有满足以下所有条件，M4.5 才视为完成：

1. `AdmissionScheduler` 不再存在同步 launch 路径或 `_worker_mode` 分支。
2. 一个 rank/GPU 的所有受控 ProcessGroup 只从同一个 worker launch。
3. rank-wide launch log 是共享 plan 的合法本地投影。
4. `ScheduledWork.wait()` 不调用任何全设备/全 stream 同步。
5. producer、NCCL 和 consumer stream dependency 在 profiler 中正确。
6. physical completion、telemetry 和 outstanding 不依赖 consumer wait。
7. launch/error/close 不会留下永久等待的未绑定 ScheduledWork。
8. 目标 GPU 上 completion capability gate 通过。
9. CPU unit/integration、3-rank cross-group harness 和 NCCL harness 全部通过。
10. README、Phase 1、architecture 和 experiment erratum 与新实现一致。

完成 M4.5 后再开始 M5 Megatron DP adapter。这样 M5 只需要适配一个稳定的
worker-only、stream-ordered scheduler contract，而不必同时兼容历史执行模型。
